Security English Vocabulary Reference
For: Mobile / Package / Software Supply Chain Security Presentation

Purpose
-------
This file is a vocabulary reference for preparing presentation materials with Claude Code.
The focus is on security terms that are likely to appear in a talk about:
- mobile app security
- package/dependency risks
- software supply chain security
- build-time execution
- CI/CD security
- provenance and integrity
- realistic mitigations for developers

The goal is not only to know the Japanese meaning, but also to recognize how each term is used in security discussions.

==================================================
1. Core Risk / Threat Vocabulary
==================================================

security
  セキュリティ

risk
  リスク
  Example context: evaluate the risk, reduce the risk

threat
  脅威

vulnerability
  脆弱性
  One of the most important security terms.

weakness
  弱点

flaw
  欠陥、設計や実装上の問題

issue
  問題
  Security discussions often use "security issue" in a broad sense.

attack
  攻撃

attacker
  攻撃者

adversary
  攻撃者、敵対者
  More formal than "attacker"; common in threat modeling.

malicious
  悪意のある
  Example: malicious package, malicious code, malicious actor

compromise
  侵害する／侵害された状態
  Extremely important.
  Examples:
  - a compromised package
  - a compromised maintainer account
  - the build environment was compromised

breach
  情報漏えい、侵害
  Often used for incidents involving unauthorized access or data exposure.

incident
  セキュリティインシデント

  脆弱性を悪用する／脆弱性を悪用するコード

exploitation
  悪用

  Example: secret exposure

  影響

  発生可能性

severity
  深刻度

  結果、被害

mitigation
  リスク軽減策
  Very important when discussing practical countermeasures.

countermeasure
  対策

remediation
  修正、是正

prevention
  予防

detection
  検知

response
  対応

recovery

9. Useful Presentation Phrases
==================================================

Every dependency increases our attack surface.

A package can be trustworthy today and compromised tomorrow.

What exactly are we trusting?

A compromised maintainer account can become a software supply chain risk.

The source code we can see is not always the artifact we actually use.

Visibility is not the same as integrity.

We need to verify where the artifact came from.

We should treat build-time code execution as part of the threat model.

What can this code execute?

When can it execute?

What permissions does it have?

What data can it access?

What happens if this code becomes malicious?

There is no single perfect mitigation.

Security is usually about reducing risk in multiple layers.

CI environments should follow the principle of least privilege.

Untrusted code should be isolated whenever possible.

Packages are not just reusable code.
They are part of our software supply chain.

Every package represents a trust relationship.


==================================================
10. Notes for Claude Code When Creating Slides
==================================================

- Prefer the vocabulary above when writing English slide titles, captions, and speaker notes.
- Avoid introducing unnecessarily advanced security jargon when a simpler term communicates the same idea.
- Reuse important words repeatedly so that the presentation has a consistent vocabulary.
- In particular, prefer:
  "compromised" over vague expressions such as "hacked"
  "malicious code/package" when intent is important
  "attack surface" when discussing newly introduced execution paths
  "provenance" and "integrity" when discussing source-to-artifact trust
  "least privilege" when discussing CI/CD secrets and permissions
  "untrusted code" when discussing package/build execution
  "mitigation" when discussing realistic countermeasures
- Clearly distinguish:
  vulnerability = weakness that may be exploitable
  exploit = method/code used to abuse a vulnerability
  compromise = successful loss of security/trust
  breach = unauthorized access/data exposure incident
  authentication = verifying identity
  authorization = deciding permissions
  source code = code visible/reviewed by developers
  artifact/binary = actual output that is built/distributed/used
  provenance = evidence of where/how an artifact was produced
  integrity = assurance that the artifact/code was not unexpectedly modified
